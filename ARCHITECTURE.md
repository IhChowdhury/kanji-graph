# Architecture

_Generated from the current codebase — describes what's actually implemented, not aspirational design._

## Data pipeline

> **Runtime loading has changed as of the Phase 1 performance-preparation pass — see `KANJIGRAPH_PROJECT.md` for the full detail.** Summary: the generator now writes `public/data/manifest.json` + `public/data/<LEVEL>/{kanji,edges}.json` (split by JLPT level) instead of flat `src/data/kanji.json`/`edges.json`, and the app loads that data at runtime via `fetch` rather than a static import.

`scripts/import-kanji-data.mjs` is the single source of truth for `public/data/*` and `public/stroke-order/*.svg`. It is **not** run automatically — regenerate with `npm run import:kanji` after placing `kanjidic2.xml.gz` and `kanjivg.xml.gz` in `scripts/downloads/` (gitignored; the script can also attempt to download them itself, but that path is unverified in restrictive network environments).

Steps, in order:
1. Parse KANJIDIC2 → meaning, onyomi/kunyomi (with compound-only `-` fragments dropped, okurigana dots joined back into the full reading), legacy JLPT digit, stroke count.
2. Parse KanjiVG → for each kanji, the *direct* child `kvg:element`/`kvg:original` values of its root stroke group (radical variants like 亻 are normalized back to 人).
3. Build the target character set: everything at the requested JLPT level(s), plus any component that is itself a real JLPT-classified kanji (unclassified Kangxi radical primitives like 一, 丨, 冖 are explicitly excluded, not defaulted to a level).
4. Build the flat entry/edge lists (entry: `kanji`, `meaning`, `jlpt`, `onyomi[]`, `kunyomi[]`, `components[]`, `strokes`; edge: `{ id, source, target }`, source = component, target = compound), then split them across `public/data/<LEVEL>/` by each entry's own `jlpt` (an edge is grouped under its *target's* level) and write `public/data/manifest.json` recording each level's availability + counts. A level with zero entries (currently N1) is recorded as unavailable rather than given an empty directory.
5. Re-scan the raw KanjiVG XML text (not the parsed object tree, to preserve exact path data) to extract each kanji's stroke-path markup, wrap it in a standalone SVG (`viewBox 0 0 109 109`, `fill:none; stroke-width:3`), and write `public/stroke-order/<character>.svg`.

`kanjiCatalog.ts` now holds only pure builder functions (no static import); `useKanjiDatasetStore.ts` loads `public/data/*` at runtime via `datasetLoader.ts`, merges whatever levels are currently loaded, and derives `rootKanjiIds` (components.length === 0) and a component→children index from the merged edge set. See `KANJIGRAPH_PROJECT.md` for the loading/caching/cross-level-edge behavior.

## State management (Zustand)

| Store | Persisted? | Owns |
|---|---|---|
| `useKanjiGraphStore` | No | Full Graph Mode's *visible exploration graph*: `nodes`/`edges` (starts with roots only), `expandedIds`, `toggleExpand` (expand/collapse with BFS-reachability cleanup on collapse so shared descendants aren't dropped early), `revealKanji` (recursively expands ancestors so search/navigation can jump to a hidden kanji). Learning Focus Mode does **not** read this store - see below |
| `useKanjiSelectionStore` | No | `selectedKanji`, `focusNodeId`, `focusToken` (incrementing token so the same kanji can be re-focused/re-centered even if already selected), `focusDurationMs`/`isExpandFocus` (drive `GraphCanvas`'s centering effect), `clearFocus` (deselect - used by "Back to Kanji List" and by `GraphCanvas`'s selection/visibility-sync effect) |
| `useGraphModeStore` | Yes (`kanjigraph-graph-mode`) | `mode: 'focus' \| 'full'` - Learning Focus (default) vs Full Graph |
| `useViewModeStore` | Yes (`kanjigraph-view-mode`) | `viewMode: 'list' \| 'graph'` - Kanji List (default) vs Graph View |
| `useJlptFilterStore` | No | `enabledLevels` checkboxes — read by the graph, Study Mode, Kanji List View, and the detail panel's visibility checks (`isKanjiVisible`) |
| `useMasteryStore` | Yes (`kanjigraph-mastery`) | `masteredIds` map + toggle |
| `useStudyModeStore` | Yes (`kanjigraph-study-mode`) | `isActive` + `completedByDate` |
| `usePracticeHistoryStore` | Yes (`kanjigraph-practice-history`) | Last 20 Writing Practice attempts per character |

**Gotcha already hit once:** any Zustand selector that falls back to a freshly-constructed array/object (`state.history[key] ?? []`) breaks `useSyncExternalStore`'s reference-equality check and causes an infinite render loop. Fix pattern used throughout: hoist a single stable `const EMPTY_X = []` module-level constant and fall back to *that* reference, never a new literal.

## Graph rendering pipeline (`GraphCanvas.tsx`)

Runs on every render, purely as derived state (no imperative "commit layout" step). `GraphCanvasInner` computes **both** modes' node/edge lists unconditionally, then picks one with a single `mode === 'focus' ? focusVisibleNodes : fullVisibleNodes` at the end - simpler than branching the whole pipeline, at the cost of some wasted work in the mode that isn't showing (not currently a measured problem).

### Full Graph Mode (`fullVisibleNodes`/`fullVisibleEdges`)

The original exploration-graph pipeline, unchanged:

1. `useKanjiGraphStore`'s `nodes`/`edges` → filtered by `enabledLevels` → `filteredNodes`/`filteredEdges`.
2. `layoutGraph(filteredNodes, filteredEdges)` (`graphLayout.ts`): splits the visible graph into connected components (a plain forest, since edges only ever run component→compound — many nodes have zero edges to each other), runs Dagre per component for real hierarchical placement, then grid-packs the resulting blocks left-to-right with wrapping. This two-level approach exists because a single Dagre pass over many disconnected single-node "components" produces one very wide row, not a readable layout.
3. `computeAncestorPath(focusNodeId, filteredEdges)` (`graphPath.ts`): BFS backward over incoming edges from the focused node, collecting the **full** ancestor set (all real parents, not one line) — drives the amber ring / animated-edge highlighting. Everything not on the path is *dimmed* (20% opacity), not removed - Full Graph Mode's whole point is showing everything that's loaded.

### Learning Focus Mode (`focusVisibleNodes`/`focusVisibleEdges`)

A separate pipeline that reads the dataset catalog directly (`useKanjiDatasetStore`'s `catalog`/`childIndex`), **not** the exploration graph above - a kanji's parents/children may never have been "expanded" into that store at all.

1. `computeLearningFocusGraph(focusNodeId, catalog, childIndex)` (`learningFocus.ts`): the focused kanji itself, its direct parents (from its own `components`), direct children, and grandchildren (children-of-children, depth 2 max) - each parent/child/grandchild edge synthesized directly, not looked up from a merged edge list. Nothing selected yet → falls back to the root kanji, so there's something to click into.
2. Filtered by `enabledLevels` (same policy as Full Graph Mode - a JLPT-disabled kanji never appears, even as someone's parent/child), then laid out with the same `layoutGraph`.
3. Nodes outside this neighborhood are **absent from the array entirely**, not dimmed - "hide unrelated nodes entirely, don't merely dim them" is the mode's whole premise. `computeAncestorPath` over just this neighborhood's edges still drives the amber "on the path to root" ring; children/grandchildren get their own teal ring tiers (`data.focusTier`, read by `KanjiNode.tsx`) instead. `KanjiNode` also hides its expand/collapse button in this mode - children are already shown automatically, so the control has nothing to do.

### Shared behavior (both modes)

- Per-node/edge style (`opacity`, `selected`, `data.onPath`, `data.focusTier`, `data.isStudyTarget`) is computed inline — transient, render-only overlays, never written back to any store.
- **Selection/visibility sync:** an effect watches whether `focusNodeId` is still present in whichever mode's node list is currently rendered. If it drops out (its JLPT level got disabled, or - Full Graph Mode - it was pruned by collapsing an ancestor), `clearFocus()` runs so the detail panel and graph can't disagree about what's selected (there is never a "selected" kanji with no visible indication of it).
- **Viewport:** selecting a kanji never calls `fitView()`/`fitBounds()` - only `setCenter(x, y, { zoom: <current zoom>, duration })`, i.e. a pure pan that preserves whatever zoom the user had. Two behaviors, chosen by `isExpandFocus` (`useKanjiSelectionStore`):
  - **Plain focus** (node click, search result, breadcrumb/parent/child chip) - centers the newly-focused node, animated over `focusDurationMs` (400ms, within the 300–500ms band). Runs for *every* plain focus, not just ones that were off-screen, so the selected node is always both centered and guaranteed visible.
  - **Expand** (`KanjiNode`'s ▶ button, Full Graph Mode only) - `focusKanjiForExpand` selects the expanded node (opening its detail panel and highlighting its learning path via the existing `selectedKanji`/`focusNodeId` machinery, for free) but the centering effect explicitly skips it (`isExpandFocus` guard) - expand/collapse never move the viewport at all, so the user's pan/zoom is never disturbed by revealing children.
- Collapsing and JLPT filter changes never move the camera either - there's simply no code path that calls `setCenter`/`fitView` for them.

`graphPath.ts` also exports `computeLearningPath`, a *separate, narrower* traversal used by the detail panel's Learning Path breadcrumb and `GraphViewNav`'s breadcrumb bar: it follows just each kanji's first-listed component, producing one line (e.g. `木 > 休`) instead of the full DAG. It takes an optional `isVisible` predicate that stops the walk before adding a JLPT-filtered-out ancestor - see "JLPT-filter consistency" below.

## JLPT-filter consistency (`data/kanjiVisibility.ts`)

`isKanjiVisible(character, catalog, enabledLevels)` is the one place that answers "is this kanji currently visible" (loaded *and* its level enabled) - shared by `GraphCanvas` (implicitly, via its own `enabledLevels` filtering), `LearningFamily` (parent/child chips), `LearningPath`, and `GraphViewNav` (both breadcrumbs), so none of them can expose a relationship the graph itself is hiding. `LearningFamily` additionally shows "Additional relationships exist in hidden JLPT levels." under a chip group when some of a kanji's real parents/children are filtered out rather than silently dropping them with no explanation.

## Kanji List View / Graph View navigation (`useViewModeStore`, `pages/HomePage.tsx`)

`HomePage` renders `Sidebar` (search, JLPT filters, mastery progress, Study Mode - always mounted, unaffected by view switching) plus one of:
- **Kanji List** (`viewMode === 'list'`, the default) - `KanjiListView`, a JLPT-filtered grid of every loaded kanji. Selecting a card calls `revealKanji` + `focusKanji` + `setViewMode('graph')`.
- **Graph View** (`viewMode === 'graph'`) - `GraphViewNav` (a "← Back to Kanji List" control plus the `computeLearningPath` breadcrumb chain) above `GraphCanvas`, with `KanjiDetailPanel` alongside.

"Back to Kanji List" calls `clearFocus()` + `setViewMode('list')` - it deliberately does **not** touch the persisted `useGraphModeStore` preference, so Learning Focus vs Full Graph is remembered independently of list/graph navigation. Search (`KanjiSearch`) also switches to `'graph'` on a result click, alongside its existing `revealKanji`/`focusKanji` call.

Dataset initialization (`useKanjiDatasetStore.initialize()`, `useKanjiGraphStore.seedRootsIfNeeded()`) lives in `HomePage`, not `GraphCanvas` - since Kanji List is the default landing view, `GraphCanvas` may never mount on a first visit, so nothing else is guaranteed to trigger the initial load. Both calls are idempotent, so this is purely a wiring change: switching views never re-fetches or re-seeds.

## Detail panel composition (`KanjiDetailPanel.tsx`)

Composes, in order: header (character + mastered check + JLPT badge + stroke-count badge) → mastery toggle → Stroke Order (`StrokeOrderPanel` → `StrokeAnimation`) → Writing Practice (`WritingPracticePanel`) → meaning/onyomi/kunyomi → Learning Family (JLPT-visible parents/children only, clickable, calls `revealKanji` + `focusKanji`; a "hidden relationships" note appears when some are filtered out) → Mnemonic → Learning Path breadcrumb (also JLPT-visibility-aware). Only ever mounted in Graph View - see "Kanji List View / Graph View navigation" below.

## Writing Practice validation & scoring (`WritingPracticePanel.tsx` + `strokeGeometry.ts` + `scoring.ts`)

Each reference stroke's real geometry comes from the actual rendered `<path>` elements: `getTotalLength()` for the true (curved) path length, and 16 points sampled along the curve via `getPointAtLength()` (not just start/end) for an accurate bounding box, all scaled from the SVG's 0–109 viewBox into the practice canvas's pixel space.

**Acceptance gate** (`passesStrokeGate` in `scoring.ts`) - a drawn stroke advances the expected-stroke index only if, compared against the **current expected stroke specifically** (never matched against the whole set), all five hold:
- direction angle (start→end vector) is within `maxAngleDiffDegrees` (70°),
- both start and end points are within `maxPointDistance` (30% of canvas size) of the reference's start/end,
- path length (actual polyline length, not straight-line start-to-end distance) is within `minLengthRatio` (0.35, i.e. 35%–~286% of the reference's length), **and**
- bounding-box IoU overlap with the reference is at least `minBboxOverlap` (0.15).

The last two were added specifically because the first two alone let a scribbled/wiggly stroke that happens to start, end, and net-point in roughly the right place score very high despite its actual shape being wrong - length and bounding-box overlap catch that a straight/simple check can't.

Direction alone was tried first and rejected during earlier development — too many kanji have multiple strokes pointing the same general way, so an out-of-order stroke would pass on direction alone. Position anchoring fixed that; length/bounding-box anchoring (added later) fixed the scribble case.

On accept: stroke redraws in green, index advances, canvas stays, and a per-stroke **Stroke Accuracy: XX%** is shown (`strokeAccuracyPercent` - the average of that stroke's direction/position/shape sub-scores, see below). On reject: canvas is wiped and redrawn from only the previously-accepted (green) strokes, same expected index stays active, red feedback shown, and the rejection is counted against that stroke slot's retry count (feeds the Stroke Order component below).

**Final score** (`computeOverallScore` in `scoring.ts`), 0–100, weighted:

| Component | Weight | Source |
|---|---|---|
| Stroke Count | 10% | accepted-stroke count vs. reference count (always 1.0 in practice under the strict gate, since completion requires exactly the reference count - computed generically, not hardcoded) |
| Stroke Order | 30% | average of `1/(1+retries)` per stroke slot - 1.0 if every stroke was accepted first-try, lower the more rejections a slot needed |
| Direction | 20% | average per-stroke angle accuracy |
| Position | 20% | average per-stroke start+end distance accuracy |
| Shape | 20% | average per-stroke length-ratio/bounding-box-overlap accuracy |

Each of Direction/Position/Shape's per-stroke sub-scores is 0 at the gate's own boundary (the worst value that still passes) and 1 at a perfect match - not a generous floor like the old direction-only formula (which gave a barely-passing stroke ~61%, not ~0%). Shape specifically combines length and bounding-box match as `(lengthScore * bboxScore) ** 2` - a product (not an average), so a stroke needs both a right length *and* a right extent to score well, squared again to suppress anything short of a good match. This is what keeps Count (10%) + Order (30%) + Direction (20%) + Position (20%) - which together can reach 80/100 "for free" on a clean, well-ordered but badly-shaped attempt - from being pushed over 80 by a merely-passable Shape score; see the regression tests in `scoring.test.ts` for the exact worked cases.

## Build & deploy

- `npm run build` = `tsc -b && vite build`. Currently one JS chunk, ~490KB minified (Vite warns about this; no code-splitting has been set up).
- `vite.config.ts` computes `base` from `GITHUB_REPOSITORY` when running under GitHub Actions, `/` otherwise — no hardcoded repo name.
- `.github/workflows/deploy.yml` builds and deploys to GitHub Pages via the native Pages Actions (not a `gh-pages` branch).
